# Where `midataworks-dataset-version.json` came from

**Not hand-written.** ADR-016: *fixtures whose fields agree by construction are how a suite
stays green over a real bug.* A manifest typed out here would agree with a buggy validator,
because both would encode the same misreading of the schema — so this one was produced by
**miDataworks' own fixture builder** and is used byte-for-byte as it came out.

|---|---|
| **Produced by** | `backend/tests/support/manifest_fixtures.py::rows_manifest()` in the miDataworks repository |
| **That repository's commit** | `4898e66fbc8288230233d21e6363343fef31198f` |
| **Taken on** | 2026-10-14 |
| **Its own provenance** | that module's docstring: *"A valid `midataworks.dataset-version/v1` document, built from the prototype's records. The counts come from `records/format_balanced.json` (2,208 / 244, 552 and 61 per cell) so the fixture is a real version's shape, not a minimal one that agrees with the schema by construction."* |
| **Serialised as** | `json.dumps(doc, indent=2, sort_keys=False)` — key order is theirs, so a reader sees the document in the order their builder emits it |

It validates against `docs/schemas/midataworks-dataset-version-v1.json` with **zero**
failures, which is the contract round-trip `backend/tests/contract/test_dataset_version_contract.py`
asserts. That assertion is the point of keeping the file at all: it is the only evidence in
this repository that miForge's reader and miDataworks' writer agree about a real document
rather than about each other's summaries.

## It is a `dataset` target, and that is deliberate

`target.kind` is `"dataset"` with `miforge_set_kind: null` — **not** a `miforge_set`. So this
file is simultaneously:

* the **valid** fixture for the validator (it conforms), and
* a **refusal** fixture for the kind map (`dataset_version_target_unsupported`), because
  miForge does not consume a general `dataset` target.

Both are real behaviours of a real document, which is better than two fixtures that each
exist to make one test pass.

## The `miforge_set` variants are *derived*, and the derivation is recorded

`backend/tests/support/part_fixtures.py` deep-copies this document and changes **exactly
two things**, each for a stated reason:

1. **`target`** — swapped for a `miforge_set` target with a `miforge_set_kind` and a
   `contract_reference`, because miForge's own ingest path needs a target it consumes and
   miDataworks' committed fixture does not carry one. Nothing else in the document is
   touched.
2. **`content.splits[].sha256`, `.bytes` and `.rows`** — recomputed from the split files the
   helper actually writes. Their fixture carries `"a" * 64` placeholders, and a digest that
   cannot match real bytes would make `verify_material` untestable: the one test that
   matters most here is that a **tampered** byte refuses, and that needs a baseline where
   the digest is right.

Every invalid variant is generated in-test by **one perturbation** of the valid document,
driven by the schema's own `required` lists — so a new required field upstream produces a
new case automatically rather than needing a hand-written fixture nobody updates.

## If this file ever stops validating

Re-vendor the schema, do not edit this file and do not edit the schema. miDataworks owns
`midataworks.dataset-version/v1` (BRD-03 R-03.47); a needed change is **requested** of them.
Regenerate this fixture from their builder at the commit you are testing against, and update
the table above.
